# Reseller API + Telegram bot — Railway deployment

This package keeps the existing bot and adds Railway deployment files for the Flask reseller API.

## Railway setup
1. Upload these files to a GitHub repository (root must contain `50.py`, `requirements.txt`, `Procfile`, and `railway.json`).
2. In Railway, create a project and deploy from that GitHub repository.
3. In the service Variables, set `BOT_TOKEN` to the current Telegram bot token. Do not commit it to GitHub. Set `STORE_API_KEY` and `MASTER_KEY` if the upstream reseller API requires them.
4. Add a Railway Volume to the app service with mount path `/data`.
5. Set variable `DB_PATH=/data/surajbot.db` so SQLite data survives redeploys. If you have an existing `surajbot.db`, copy it into the mounted volume before relying on the new instance; a fresh deployment creates a new database and will not automatically contain your old products/users.
6. Wait for deployment to succeed, then open service Settings → Networking → Generate Domain. Railway will provide the public HTTPS URL.
7. Test `https://YOUR-DOMAIN/api/health`, then `https://YOUR-DOMAIN/api/docs`.

## API endpoints
- `GET /api/health` — health check
- `GET /api/docs` — API documentation
- `GET /api/me` — authenticated reseller details
- `GET /api/products` — authenticated products and plans
- `POST /api/buy` — authenticated product/duration purchase

Use `X-API-Key: <reseller-api-key>` for authenticated endpoints.

## Important
- A public URL is generated by Railway after deployment; this package cannot create the URL from here because it requires access to your Railway account.
- Railway's default filesystem is ephemeral. The `/data` volume and `DB_PATH` variable are needed to preserve SQLite data across deployments.
- Keep bot/API secrets in Railway Variables, never in a public GitHub repository. If a token was exposed in a ZIP or public repo, revoke it with BotFather and use a new one.
